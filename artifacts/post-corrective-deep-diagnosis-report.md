## Outcome and evidence

The now-running Ollama 0.34.2 with **qwen3:8b** made the live failure reproducible. Direct and bridge tags/tiny structured calls and bridge health succeeded; local bridge CORS/route restrictions worked for the tested origins/routes. Of 13 graph-mutation operation families, **nine remained invalid after one repair** on the latest run, and four succeeded only on repair. The preceding run failed 10/13, showing model variance without reliable contract success. No model response was applied to the graph. A controlled invalid-first/repair-timeout sequence demonstrated why a user can see `model_generation_timeout` even though the first structured response failed validation. The unchanged Node suite passed **249/249** after the bundled Python and Node were put on PATH.

The most consequential root cause is a contradictory GraphMutationDraft contract: the model-facing schema requires every operation property, while the deterministic validator rejects populated properties irrelevant to the chosen operation. qwen3:8b dutifully fills the required keys; repair repeats the same format. This is availability failure with a sound fail-closed commit boundary, not a reason to relax the graph validator. A narrow experimental `oneOf` format passed 6/6 local trials for two families, but cannot be assumed production-safe until the exact full schema passes all families and backend variants.

Two security candidates were confirmed by source/probe with explicit conditions: a parsed Custom Parser `ImportExpression` escapes the static guard (parser code still requires user approval before running), and initial private Ollama URL validation does not constrain fetch redirects (a redirecting local endpoint is a precondition). Neither path was used to exfiltrate data or run a hostile parser. Security preflight passed, but the 1,074-file repository-wide security scan was **not completed**; this report does not claim exhaustive security clearance.

Overall status: the diagnosis produced **16 confirmed or source-backed issues** (1 HIGH, 11 MEDIUM, 4 LOW), grouped below. It is complete for the checks that could be run in this Windows environment, but **not an exhaustive application qualification**: file-picker automation, WSL/CUDA Runtime Companion, and the formal repository-wide security scan were unavailable/incomplete. These boundaries are recorded rather than silently counted as passes.

## Browser and domain audit

The live browser audit used Vite at `127.0.0.1:5178`. The bundled H2V example converted to 3 hyperedges, 5 vertices, 9 incidences; graph version/fingerprint changed on a subsequent conversion. Blank input failed without replacing the prior graph. Circular, Grid, and Line Graph previews rendered; line-graph-specific controls behaved as expected. A custom preview limit of zero was rejected with a 1–10,000 bound. Statistics showed one line-graph triangle, 60% incidence density, and 90% V2V density, yet the conversion summary falsely said triangles were too large to count (D08). CANDY exposed 30 classes, with six open-wedge and 24 closed-triangle classes in this small view; computation was unavailable because the native Runtime Companion was off. No CPU fallback was claimed.

Batch Updates previewed ADD_VERTEX h0:6 as 6 vertices/10 incidences while the committed graph remained unchanged. Discard returned to the committed view. The separate Commit Batch Changes control is intentionally available without a prior preview and internally validates; no commit was clicked during diagnosis. Deterministic chatbot help and read-only stats made zero model calls. “Add vertex 6 to h0” staged a confirmation preview, and Cancel left the committed graph intact. The model planner's failed structured draft did not bypass the confirmation gate. Thread memory persisted across reload while pending graph authority did not; source inspection confirms persistence strips live actions and requires re-upload for file authority. Multi-tab/quota cases remain untested.

Every visible Advanced Diagnostics control was exercised: full/reconnect, direct/bridge isolated probes, planner, simple generation, five copy controls, and GitHub Pages help. Full diagnostics short-circuited after direct success instead of testing all advertised rows (D04). The bridge isolated probe succeeded but displayed the active direct endpoint (D05). Later probes reset prior rows, copied report omitted live failures, and the copied origin command used POSIX syntax despite a Windows UI (D06, D15). Untrusted bridge Origin received 403, permitted Origin received CORS response, and an unlisted route 404. The visible Connect action failed when assist was disabled until an unrelated exact enable command was used (D07).

Custom Parser with no uploaded files ran to an empty result, then showed a green “0 hyperedges parsed” preview and enabled Apply, although its handler would reject zero edges (D09). Static guard inspection and a parse-only diagnostic script confirmed `ImportExpression` is accepted (D10); **no import was executed**. Upload policy enforces 50 files, 10 MiB each, 50 MiB aggregate, extension list, and three concurrent readers, with cancellation checks. It accepts duplicate filenames; downstream maps/profiles use filenames as keys, creating identity ambiguity (D14). Two attempts to drive the browser file chooser timed out in the automation surface, so no live file upload, uploaded batch mapping, or model-generated parser-on-files was claimed.

The graph/hypergraph state and visualization paths showed no confirmed mutation bypass. Preview, summary, statistics, CANDY adapter, deterministic NLU, orchestrator, upload batch activation, and workspace/thread state were reviewed for stale authority. The ReAct loop is bounded to eight steps and uses typed deterministic execution and confirmations. The CANDY native contracts, motif taxonomy, job state, content-addressed artifacts, and incremental capability are covered by source/tests, but Runtime Companion on port 8791 refused connection, CUDA compiler was absent, WSL service access was denied, and feature flag was false. ## Bridge, launchers, and security boundaries

The bridge binds loopback 8787 and routes only health/tags/chat; tested CORS allowlist and body/response/time budgets were effective. Direct browser Ollama and bridge connection both worked with explicit 5178 origin. Windows `run-with-ollama.bat` uses ambient `where ollama/npm/node`, launches a minimized bridge, treats any HTTP 200 health as readiness, prints 5173 even if Vite moves to 5178, and lacks a port/origin handshake. Shell launchers also assume ambient binaries and static 5173. This is a portability/readiness diagnosis (D16), not evidence that the bridge protocol failed in the tested configured environment. The origin setup clipboard command is POSIX-only (D15).

Security properties inspected: bounded file previews and upload caps; deterministic graph confirmation and stale-snapshot checks; parser Worker with time/output limits and intended global shadowing; local/private model endpoint checks; bridge loopback/CORS/route limits; CANDY bearer token and exact origins; thread persistence without pending authority. Conditional gaps D10 and D11 need an explicit corrective security phase. No `SECURITY.md` was found; native qualification records are local consistency evidence rather than signatures. The [test-gap analysis](./post-corrective-deep-diagnosis-test-gap-analysis.md) separates verified safeguards from missing adversarial and end-to-end coverage.

# v7.3.14 Stage 3 — Canonical Incidence Index Foundation

## Scope and checkpoint

Stage 3 begins directly from approved Stage 2 final corrective commit `e84732d773584b99592ae827b0e33616aecde090`. This is an infrastructure-only change. It adds one pure incidence-index module and does not migrate algorithms, preview topology, mappings, App state, graph mutation, workers, or assistant behavior.

## Architecture characterization

Before the production edit, no reusable explicit incidence index existed. `src/graph/entityResolver.js` had a partial resolver-specific index, but it string-coerced identifiers, stored incident IDs in duplicate-sensitive arrays, lacked `hyperedgeToVertices`, and had no explicit ordering or immutability contract.

Independent incidence-like work currently exists in:

- `src/utils/mappings.js`: V2H, H2H, H2H estimation, statistics degree maps, and triad support.
- `src/algorithms/projection.js`: pairwise V2V projection.
- `src/algorithms/graphModel.js`: projected adjacency and independent vertex collection.
- `src/components/Viz.jsx`: vertex collection and membership scans for preview selection.
- `src/graph/entityResolver.js`: resolver-specific hyperedge/vertex lookup.
- `src/App.jsx`: V2H memoization and independent vertex-count summaries.

These consumers remain unchanged for their later authorized migration stages.

## Incidence index contract

`src/graph/incidenceIndex.js` provides:

- `buildIncidenceIndex(canonicalHyperedges)`
- `getIncidentHyperedgeIds(index, vertexId)`
- `getHyperedgeVertexIds(index, hyperedgeId)`
- `hasVertex(index, vertexId)`
- `hasHyperedge(index, hyperedgeId)`

The returned structure exposes deterministic `vertices` and `hyperedges` arrays plus read-only `Map`/`Set` views for `hyperedgesById`, `vertexToHyperedges`, and `hyperedgeToVertices`. It includes exact hyperedge, vertex, and unique-incidence counts.

The builder accepts already-canonical identifiers only. It reuses the Stage 1 validator, rejects identifiers that would require normalization, never trims or stringifies IDs as an index policy, and preserves whitespace, literal quotes, commas, leading `#`, Unicode, emoji, literal `null`, zero, and prototype-like identifiers exactly.

Hyperedge records remain canonical references, so weight `0`, time `0`, attributes, and other metadata remain reachable unchanged. Duplicate memberships are removed only from derived relations. Empty hyperedges remain indexed with empty membership; singletons create one incidence and no projected self-loop.

## Ownership and invalidation

The canonical hyperedge array remains the only source of truth. The index has no mutation methods, module-global state, singleton, or cache. In Stage 3 it is rebuilt explicitly from each canonical state. Mutation-path tests cover add/remove hyperedge, add/remove incidence, rename hyperedge, rename vertex, replacement, clear, and undo/restore. Existing `graphVersion`/fingerprint ownership is unchanged.

Measured with Node `v24.19.0` on `win32/x64`. These are local measurements, not browser scalability claims.

| Fixture | H | V | I | Median build | Map entries | Set entries |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| TinyBasic | 2 | 4 | 5 | 0.0020 ms | 8 | 10 |
| LargeSparse | 10,000 | 10,001 | 20,000 | 12.1481 ms | 30,001 | 40,000 |
| OneHugeEdge1K | 1 | 1,000 | 1,000 | 0.1722 ms | 1,002 | 2,000 |

| DuplicateOverlap | 200 | 46 | 9,200 | 1.1278 ms | 446 | 18,400 |

Map entries equal `2H + V`; Set entries equal `2I`. OneHugeEdge5K stores 10,000 bidirectional Set entries rather than 12,497,500 clique pairs. DuplicateOverlap stores 18,400 bidirectional Set entries rather than constructing 207,000 naive candidate V2V operations. A dependency regression proves the builder imports no projection, mapping, or graph-model module and invokes no H2H/V2V builder.

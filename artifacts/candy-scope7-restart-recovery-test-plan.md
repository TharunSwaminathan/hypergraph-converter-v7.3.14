# Scope 7 — restart, recovery and adversarial qualification plan

Target inspected: `335c320a052eab48d3f0c2d309805d10a5918189`. This is a **future implementation test plan**, not evidence that browser crashes, Windows restarts or new persistence features have been qualified. Current executed evidence is limited to the baseline gate receipts and eleven focused production-module probes under `candy-scope7-readiness-work/`.

## Harness, fixtures and evidence rules

Use isolated browser profiles and explicitly owned temporary project/Runtime roots; never clear a user's real site data, kill an unrelated process or mutate qualified native inputs. Record exact product SHA, browser/OS/version, actual origin, storage policy, project/schema/revision, fixture seed, source/graph/result digests, save acknowledgements and failure-injection boundary. Hash logs after completion. Preserve NON-PASS attempts and counterexamples.

Fixtures: (1) tiny known hypergraph; (2) DynamicHypergraph with staged insert/delete/replacement and all 30 expected signed bins; (3) two same-name/same-size files with different bytes and renamed identical-byte controls; (4) parser draft/profile plus validated and invalid outputs; (5) two projects/tabs with distinguishable messages; (6) exact upload-boundary and oversize datasets; (7) immutable historical result with a provenance manifest and independent digest substitutions. Use synthetic, non-secret tokens only in persisted attack fixtures.

Observe both UI and deterministic owners. A historical label alone is insufficient: assert missing bytes are unavailable, graph/current-result identities are correct, no action token is restored, graph mutation count is zero until a new explicit confirmation, no native job is created by restoration, and no cloud request is emitted. Log outgoing destination/method and authority transitions without credential/header/body leaks. Use model/Runtime doubles for deterministic fault coverage; separately qualify real browser storage and genuine qualified local backends where the gate calls for them.

For crash tests, distinguish: enqueue, transaction issue, request success, transaction complete, manifest publication and explicit durable-save acknowledgement. A request success callback is not a commit receipt. Kill only the test-owned browser/application/Runtime. Physical power/Windows restart requires a separately scheduled human-controlled window, not automatic shutdown during ordinary tests. Never claim OS power-loss behavior from a mock or normal unmount.

## Existing evidence and limitations

The current baseline already has source-backed authority-stripping and queue-bounding tests (`tests/candy-scope5-persistence.test.mjs:14`), mounted React restoration (`tests/candy-scope5-recovery.test.mjs:59`) and execution-owner multitab separation (`tests/candy-scope5-multitab.test.mjs:1`). These use transactional IDB doubles/happy-dom or fixture Runtime; they do not prove browser storage durability, full chat merge, physical reboot safety or effective Windows ACL privacy. The fixture explicitly states that limit: `tests/fixtures/candy-scope5e-storage.mjs:1`.

Audit probes P01–P04 exercised projection/bounds/schema; P05 demonstrated stale whole-record overwrite; P06 demonstrated dropped queued save on dispose; P07 silent settings failures; P08 profile validation/bounds; P09 legacy-key survival; P10 config/hint/transport resolution; P11 distinct URL origins and CANDY allowlist mismatch. No live model, native backend or user's browser profile was touched by these probes.

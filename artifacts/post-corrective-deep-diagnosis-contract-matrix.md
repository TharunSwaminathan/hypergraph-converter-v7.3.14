The canonical row-by-row record is [`post-corrective-deep-diagnosis-live-ollama.json`](./post-corrective-deep-diagnosis-live-ollama.json). On the latest run, `ADD_INCIDENCE`, `REMOVE_INCIDENCE`, `ADD_HYPEREDGE`, `RENAME_VERTEX`, `RENAME_HYPEREDGE`, `REMOVE_VERTEX_GLOBAL`, `REMOVE_HYPEREDGE_ATTRIBUTE`, `CLEAR_GRAPH`, and `UNDO_LAST_MUTATION` failed first and repair validation. `REMOVE_HYPEREDGE`, `SET_HYPEREDGE_WEIGHT`, `SET_HYPEREDGE_TIME`, and `SET_HYPEREDGE_ATTRIBUTE` repaired to valid drafts. `REMOVE_HYPEREDGE` failed on the preceding run, demonstrating model variance without contract reliability. The bridge ADD_INCIDENCE first attempt reproduced the same eight irrelevant-field errors. The non-mutation prompt repaired to `clarification`, not `not_mutation`; preview-only failed; a synthetic pending correction validated once but produced `previewOnly:true`, which requires a separate intent-level test before being called a defect.

The experimental narrow `oneOf` operation schema passed 3/3 ADD_INCIDENCE and 3/3 CLEAR_GRAPH trials in [`post-corrective-deep-diagnosis-schema-variant.json`](./post-corrective-deep-diagnosis-schema-variant.json). This is feasibility evidence, not proof that qwen/Ollama supports every JSON Schema feature or that a production replacement is safe. A corrective phase should compare an exact operation-variant schema, server acceptance, all 13 operation families, repair behavior, and validator closure; do not simply permit irrelevant populated fields.

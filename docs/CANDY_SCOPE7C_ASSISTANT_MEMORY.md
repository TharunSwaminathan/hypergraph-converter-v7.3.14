# Scope 7C: project Assistant memory

Memory is explicit, local project data, separate from the conversation transcript and the authoritative Scope 7B workspace. It is independent of Ollama connectivity. No cloud API, embedding service, vector database or Git metadata is required.

## Controls and API

Open Assistant → Project Assistant memory. Select a semantic type and a short topic key, enter a compact statement, then Remember. The status distinguishes pending from committed persistence. Inspect shows original text, provenance, lifecycle, revision, conflicts and stale linkage. Replace with editor text explicitly supersedes an active record. Forget, Forget selected category and Clear project memory erase the selected text without deleting graph/source objects or other projects. These controls are deliberately basic; polished project opening/resume UX remains 7E.

The Assistant recognizes `Remember that …`, `show project memories`, and `forget memory <UUID>` deterministically, without a model. Natural Remember uses USER_DECISION/topic `general`; use the typed controls for specific topics. Multiple incompatible statements under the same type/topic are conservatively marked CONFLICT and excluded from recall until the user resolves them. There is no general semantic contradiction detector. No automatic extraction from conversation or automatic workflow continuation is performed. Memory commands are intercepted before transcript persistence; rejected credential-like input on this path is not copied to chat.

`createProjectStore().readMemory(projectId)` validates and hashes the project collection. `saveMemory(projectId, expectedProjectRevision, command, isCurrent?)` supports remember, supersede, forget, forgetType and clear. App callers share `createProjectSession` with chat and workspace writes; independent tabs never rebase stale revisions. `createMemoryCoordinator(store, projectId)` exposes initialize, inspect, context, mutate and dispose. Changing a project disposes its owner and suppresses obsolete receipts. A transaction already submitted may finish for the old project; it cannot publish success into a new project. Programmatic project selection is supported; no new workspace-switch/resume screen is introduced.

## Schema and provenance

Database `hypergraph-studio-projects` upgrades additively from v2 to v3, adding `assistantMemories` keyed by projectId. The existing seven stores, project schema and workspace schemas remain unchanged. Opening a future database version fails closed. Old v2 clients receive VersionError after upgrade; they cannot downgrade it.

Envelope schema 1 contains projectId, schemaVersion, revision, records and SHA256. Each record contains memoryId, projectId, memoryType, schemaVersion, topic, content, createdAt, updatedAt, revision, status, provenance, sourceRefs, importance, confidence, supersedes and contentDigest. IDs are application UUIDv4 values. Record revision identifies creation of the immutable statement; lifecycle/erasure updates advance the envelope and project CAS revision. Replacement creates a new statement and preserves the predecessor as SUPERSEDED. Forgetting retains bounded identity/supersession bookkeeping with empty content and sourceRefs. Clear resets that bookkeeping; the project revision still prevents stale resurrection.

Types: PROJECT_SUMMARY, PROJECT_GOAL, USER_DECISION, USER_CONSTRAINT, WORK_COMPLETED, CURRENT_STATUS, OPEN_ISSUE, NEXT_STEP, REFERENCE, PROJECT_PREFERENCE, TECHNICAL_FACT, RESULT_SUMMARY and ASSISTANT_NOTE. Types classify compact text, never arbitrary objects or authoritative analysis payloads.

Origins: USER_EXPLICIT (USER_STATED), WORKSPACE_DERIVED/SYSTEM_DERIVED (DETERMINISTIC), ASSISTANT_INFERRED/IMPORTED (UNVERIFIED). Explicit user writes do not silently promote model summaries. The programmatic inferred/imported categories do not implement automatic extraction or an archive importer. Workspace capture ignores caller-supplied factual text: it computes a fixed source-count/graph-cardinality/fingerprint statement from verified saved 7B bytes, linked to project ID, root SHA256, graph fingerprint and source SHA256 values. Unknown cardinality is unavailable, never numeric zero. SYSTEM_DERIVED similarly uses a fixed application-policy statement. Current source/graph changes, uncommitted live workspace edits or failed restoration suppress derived recall. User-explicit context can remain available when the workspace is unavailable.

Content digests are SHA256 of canonical JSON string values; envelope digests cover canonical JSON excluding the digest field. They detect corruption, not malicious same-origin code with permission to rewrite application data. Provenance is a validated application origin label, not a cryptographic attestation of a human statement.

## Concurrency, durability and bounds

Hash preparation happens outside IndexedDB transactions. The write rechecks project CAS, tombstone, exact prior memory envelope and live owner before publishing memory and project revision atomically with a valid thread. Acknowledgement resolves only on transaction completion, never request success. Quota/abort preserve previous committed state. Read-side validation rechecks memory digest and workspace root; unrelated chat-only revisions do not spuriously invalidate recall. Entire-project deletion and application clear remove owned memory through the existing tombstone lifecycle.

Limits: 2,000 UTF-16 content characters and 8,000 UTF8 bytes per statement; 100 records including historical/forgotten bookkeeping; 32 ACTIVE; 256 KiB serialized memory/project. Reaching retention limits requires explicit clear/forget or supersession as applicable, never eviction of authoritative sources/graphs. The existing maximum of 80 projects bounds total memory to at most 20 MiB logical payload, independently of the 7B workspace budget. Browser storage estimates are advisory; quota failures remain explicit. Browser eviction, private-mode loss and physical power-loss/fsync durability are not guaranteed by transaction completion.

Recall loads only the active project and selects ACTIVE, non-stale, non-conflicting records. Order: importance descending, explicit-user before other origins, creation revision descending, UUID as deterministic tie-breaker. At most eight records, two/category and 6,000 serialized item characters are admitted. Whole records are skipped when over budget; content is never silently truncated. Omission, conflict and stale counts are exposed. These are deterministic structured filters, not vector similarity or a claim of general semantic relevance.

Only the ordinary conversation request receives a separate normalized `projectMemoryContext` in its user-role JSON data. The static system contract identifies it as untrusted contextual data. Raw envelopes are not injected. Memory is deliberately excluded from action planners and all confirmation/Apply/Runtime authority channels. Current deterministic observations win. Rendered text uses React escaping; HTML is not interpreted. Stored instructions, “yes”, approval, parser code or Runtime liveness cannot be replayed into execution authority.

## Privacy and qualification limits

Explicit memory writes reject obvious password/API-key/Bearer/auth/session/Runtime credential assignments, common token formats, private keys and standalone temporary approvals. The text and topic key both pass the safety filter. This conservative heuristic is not universal secret detection; false negatives and false positives remain possible. There is no background extraction and no model-service credential persistence. Do not deliberately save sensitive project text. Existing chat retention and browser-origin security remain separate contracts.

Scope 7C qualification distinguishes transactional doubles, mounted happy-dom tests, actual isolated Chrome/App/native IndexedDB, injected quota faults and actual manually connected local Ollama requests. Profiles are synthetic and guarded; no real user stored workspace is accessed. Logical maximums are policy, not arbitrary-scale performance claims. Full workspace archive export/import, historical motif-result archives, automatic model reconnect (7D), polished Resume UX (7E) and the full physical restart/power-loss matrix (7F) remain deferred/partial. Existing Runtime authentication, CUDA separation/fail-closed behavior, graph algorithms, explicit mutation confirmation and parser review/Run/Apply remain unchanged.
